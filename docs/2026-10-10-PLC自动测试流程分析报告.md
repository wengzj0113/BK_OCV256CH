## 2. 正常流程时序

轮询：`PlcAutomaticTestCoordinator.vb:112`，`System.Threading.Timer` 1000ms，`Interlocked.Exchange(pollBusy,1)` 防重入。每个 tick **独立**读取 R150/R151/R152（`:149-151`），不以当前状态为门控——这是 2026-10-07 独立寄存器文档的要求，覆盖了 v3/v4 计划里"按状态分别轮询"的旧设计。

| 步骤 | 代码位置 | 行为 |
|---|---|---|
| 1. 上升沿捕获 | `:157-183` | 读成功且为高且 `rXXXRequestConsumed=False` → 置 `rXXXRequestConsumed=True` 并挂 pending。读到低电平才重新武装。首次采样即为高也算有效（`:34-36` 注释）。 |
| 2. R150 → 扫码 | `:241-280`, `:435-472` | 条件 `trayRequestPending AndAlso Not trayPreparationInProgress AndAlso Not manualTrayCodePending AndAlso cycle.TrayCode 为空 AndAlso 过了重试时刻` → `TriggerScan()` + `ReadTrayCode(1500)`。 |
| 3. 托盘码校验 | `frmTest.vb:2426-2431` | 非空 + 长度等于 `Initsetting.txtCodeLenth`（配置为 0 时不校验长度）。失败 → 弹手工输入框；取消 → 2 秒后自动重扫（`:508-520`）。 |
| 4. 托盘准备 | `frmTest.vb:1494-1517` | 清 `activeTrayPlan` 与 256 个 `BatCode` → 调试模式走 `CreateDebugTrayPlan`；正式模式走 `OcvDataService.GetTrayCellsByTrayCode` + `TrayTestPreparation.Prepare`。自动模式 `MeasurementChannels = 1..256`（`TrayTestPreparation.vb:44-45`）。 |
| 5. 计划校验 | `TrayTestPreparation.vb:26-42` | 空通道号、非法通道、重复通道、重复电芯码、0 行有效电芯码 → `InvalidOperationException`。 |
| 6. 提交 + R160 | `:522-571` | 提交 `cycle.TrayCode` → `plc.WriteR160()`（要求 WC 应答）。失败 → 停 `WaitingR150Reset`，下一轮只重试 R160，**不重查库、不重建计划**。 |
| 7. R151 → 测试 | `:288-329` | 需 `cycle.TrayConfirmed`；`CanStartAutomaticTest`（`frmTest.vb:2409-2424`）要求 `activeTrayPlan.MeasurementChannels.Count = 256` 且 SCM / 3561 / 34461 通讯正常。 |
| 8. 初测 + 复测 | `:573-651` | `StarTest(1,...)` → NG 集合 → 按 `cmbRetestNum` 轮次复测（`StartRetestPass`）。 |
| 9. 结果发布 | `frmTest.vb:2560-2594` | 单次 OCV_DATA 任务（Create → SaveResults → 本地 CSV → Complete）+ 正式模式下 MES 后台上传。调试模式跳过 MES。 |
| 10. R161 + 释放托盘 | `:712-755` | 写 R161；`RequiresNgSorting`（`currentOCVNum = 1`）时把 NG 集合存入 `pendingNgSelection`；`cycle.Reset()` → Idle，允许下一托盘扫码（与上一托盘 R152 握手**可重叠**，见 `:32-33` 注释）。 |
| 11. R152 → 分选 | `:331-377`, `:669-710`, `:757-839` | 上升沿**同时快照**当时的测试状态（`CaptureR152TestStateLocked`）：`NoTestStarted` → 直接写 R162；`TestInProgress` → 暂存待 R161；`TestCompleted` → 升序写 `DT(1000+通道)=2`（逐点 WC 应答、已写点位重试时跳过）再写 R162；`TestFaulted` → 不写 R162，等人工。 |
| 12. 停止 | `:386-413` | `RequestStopCurrentCycle`：代次 +1、清空所有 pending、`cycle.Reset()`、状态回 Idle。 |

## 4. 问题清单

### P1 — 托盘准备失败不可恢复（HIGH）

**现状链路：**

1. `PrepareTrayForTest` 在查询**之前**就清掉 `activeTrayPlan` 和全部 256 个 `BatCode`（`frmTest.vb:1497-1501`）。失败后界面与内存里既没有旧托盘数据，也没有新托盘数据。
2. 查询或校验抛出的任何异常沿 `AcceptTrayCode` → `BeginTrayCodeRead` 冒泡到 `ProcessPendingRequests` 的 `Catch`（`:273-274`），直接 `EnterFault`。
3. 此刻的现场：`r150RequestConsumed = True`、`trayRequestPending = False`、`cycle.TrayCode` 为空、`activeTrayPlan = Nothing`、状态 `Fault`。
4. `chk_Test` 在 `Fault` 下**允许**切换（`frmTest.vb:1543-1552` 只挡 Idle/Fault 之外的状态），但切换只清缓存 + 改标志（`:1554-1561`），**不会重做本次托盘准备**。
5. `Fault` 下轮询仍在跑，但 R150 保持高电平不会再次触发；只有读到 R150=0 才重新武装。

**结果：** 操作员唯一出路是让 PLC 把 R150 拉低再拉高（或按停止后等 PLC 复位）。数据库短暂不可用、托盘映射漏数据、托盘数据重复等**本可原地重试**的场景，都被升级成整机流程故障。

### P5 — 停止后仍可能下发上一托盘的 NG 分选（需现场确认）

`RequestStopCurrentCycle`（`:386-413`）清空了 `cycle`，但**不清理 `pendingNgSelection`**。若停止前上一托盘的 NG 交接尚未收到 R152，之后 PLC 再发 R152，协调器仍会写 `DT=2` 并回 R162（`:331-377` 的 `startSorting` 分支）。

代码注释（`:32-33`、`:754`）表明"上一份 NG 结果保留至 R152"是有意设计；但操作员按"停止"时是否期望仍然向 PLC 下发这批分选结果，需要在现场握手确认。现有回归脚本 `Test-PlcCycleRecoveryRuntime.ps1` 只覆盖"测试未开始时停止"（R162Writes=0），未覆盖此场景。

### P6 — 文档内部矛盾（LOW）

`2026-10-07-plc-customer-handshake.md` Task 4 要求"R162 ACK 前下一次 R151 不启动测试"，但更晚的 `2026-10-07-plc-independent-register-processing.md` 要求"早到的 R152 不得清除尚未执行的 R151 请求"，代码按后者实现（`:291` 只要求 `TrayConfirmed`，下一托盘可与上一托盘 R152 握手重叠；`pendingNgSelection` 只阻塞下一轮的 **R161**，`:716-724`）。以较晚文档为准，两者不冲突，但计划文档未标注废止。

**三处关键缺口（仍未满足计划要求）：**

1. **重试只能靠调试模式，正式模式下没有入口。**
   `RequestTrayPreparationRetry` 第一行即 `If Not host.IsDebugModeEnabled() Then Return`。UI 只有 `chk_Test.CheckedChanged` 一个触发点，Designer 中**没有"重试准备"按钮**（`frmTest.Designer.vb` 的改动只是 `chk_Test` 重排）。
   而调试模式重试走的是 `CreateDebugTrayPlan`，生成 `TEST-<日期>-<通道>` **假电芯码**，不是重查数据库。因此计划 §4.4 明确要求的场景——"数据库或托盘数据修复后，操作员点击重试，**在当前模式下**重查同一托盘码"——**做不到**：数据库修好后只能等 PLC 把 R150 拉低再拉高。

2. **失败分类完全未做，用 `Catch ex As Exception` 一把抓。**
   `PrepareTrayAndConfirm` 只包住 `host.PrepareAutomaticTray`，捕获**所有**异常并转入恢复状态。计划 §4.2 原文即"分类必须基于具体来源，**不得用 `Catch Exception` 把所有异常变成可恢复状态**"，并要求 `TrayPreparationException` / `TrayPreparationFailureKind` 区分 `NoBatteryMapping` / `InvalidTrayData` / `DataAccessFailure`，未分类异常仍转 `Fault`。

3. **候选计划原子提交未做。**
