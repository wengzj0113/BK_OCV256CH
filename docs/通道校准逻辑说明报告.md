# 通道校准逻辑说明报告

**报告范围：** `FrmChannelCalibration` 校准页面，以及校准值在正式测试中的使用方式。  
**依据：** 当前工作区 VB.NET 源码。本文区分源码设计的业务流程和源码中发现的界面绑定风险。

## 一、结论摘要

这套校准的目的，是给 256 个设备通道分别计算一个内阻补偿值。校准时，将已知标准电阻接入通道，读取日置 3562 的实测电阻值，再按下面的公式求补偿量：

```text
补偿值（mΩ）= 标准电阻（mΩ）− 实测电阻（mΩ）
```

例如标准电阻为 3.750 mΩ，3562 测得 3.820 mΩ，则该通道补偿值为 −0.070 mΩ。正式测试回填内阻时，程序把实测内阻与该通道补偿值相加，使结果向标准值修正。正式测试本身另由一套流程读取 3562 内阻和 34461 电压；校准页只计算内阻补偿。

校准页只采集内阻，不在本次校准中采集电压。补偿值存在 256 项全局数组中，并写入本地 CSV；数据库可用时，也会写入 OCV_DATA。

## 二、相关组件和职责

| 组件 | 职责 |
|---|---|
| `FrmChannelCalibration.vb` | 页面权限检查、输入验证、通道选择、调用校准、更新表格、保存和记录操作日志 |
| `ChannelCalibrationRunner.vb` | 按通道生成中位机计划、启动设备、读取 3562 缓存、计算每个通道的补偿值 |
| `CalibrationService.vb` | 维护 256 项补偿数组；从 CSV/数据库加载；校验并保存补偿值 |
| `SerialMiddleMachineClient.vb` | 通过串口配置中位机通道计划、启动测试并等待完成 |
| `InstrumentCacheParser.vb`、`Module1.vb` | 读取并解析 3562 缓存；把 3562 返回的 Ω 转换成 mΩ |
| `FormalTestRunner.vb`、`TwoPassResultMapper.vb` | 正式测试读取电阻、电压，并将通道补偿值加到电阻读数上 |

## 三、页面打开与校准值加载

1. 页面打开时先检查“通道校准”权限；没有权限则关闭页面。
2. `CalibrationService` 使用 `%LOCALAPPDATA%\XL_OCV_256CH\CalibrateArr.csv` 作为本地文件。文件不存在时会创建包含 256 个零值的文件。
3. CSV 每行对应一个通道，按通道顺序保存数值，不带表头。文件中的无效数值按 0 处理。
4. 若 OCV_DATA 可访问，程序把数据库中的有效校准值覆盖到 CSV 加载结果上；因此加载时数据库值优先。数据库未初始化或 SQL 不可用时，代码保留本地 CSV 作为回退来源。
5. 加载后的 256 个值写入全局数组 `calibrateValueArray`，再按通道号填入表格的“当前补偿值”列。
6. 页面顶部的标准阻值优先采用已保存的 `Initsetting.cailibrateModelValue`；该值未设置或不大于 0 时，默认使用 3.75 mΩ。

页面重新打开和点击“读取校准值”都会重新加载数据。注意，当前加载代码会把每行状态显示成“未校准”，不会根据已有补偿值恢复历史校准状态；所以“未校准”更接近本次页面尚未执行校准的状态，不等于该通道一定没有已保存补偿值。

## 四、通道选择和输入规则

当前表格 8 列的含义如下：

| 表头 | 含义 |
|---|---|
| 选择 | 勾选本次要校准的通道 |
| 通道号 | 设备物理通道号，范围 1–256 |
| 当前补偿值（mΩ） | 当前已加载/已保存、正式测试会使用的补偿量 |
| 实测电阻（mΩ） | 本次校准由 3562 读出的标准件测量值 |
| 标准电阻（mΩ） | 顶部输入的本次标准件阻值 |
| 本次补偿值（mΩ） | 按“标准电阻 − 实测电阻”计算出的新补偿量 |
| 校准时间 | 本次校准结果对象记录的系统时间 |
| 校准状态 | 本次页面操作状态，例如未校准、校准中、已校准或错误信息 |

“当前补偿值”是现行值，“本次补偿值”是本轮新算出来的值；校准成功后，新值会复制到当前补偿值并保存。单通道校准时间在启动硬件前记录；批量校准时间在读回缓存后的结果映射阶段逐项记录。

- 选择逻辑设计为按起始、结束通道选择闭区间，例如 1 到 16；允许的通道范围是 1 至 256。
- 也支持全选、取消选择、勾选单个通道。
- 点击“校准选中通道”时，如果没有勾选任何通道，代码会尝试使用表格当前行作为目标通道。
- 标准阻值必须是可解析的正数；它是本次所选通道共用的标准值。
- 保存按钮和清零操作针对 256 个通道的当前补偿值列，不只针对勾选的通道。勾选范围只决定本次测量哪些通道；清零先改界面值，需保存后才写入持久化存储。

## 五、单通道校准流程

单个通道被选中时，事件处理代码定义了以下步骤。当前源码的列名不一致可能使页面在访问行状态前就失败，详见第九节：

1. 将该通道标记为“校准中”，并滚动到对应行。
2. 把界面通道号转成从 0 开始的数组索引，生成仅包含该通道的中位机计划。
3. 启动中位机计划，等待完成；校准流程等待上限为 300 秒。中位机报告错误、等待超时或缓存读取失败都会进入失败处理。
4. 从 3562 读取 1 条内阻缓存。解析器将 3562 返回的 Ω 乘以 1000，转换成 mΩ。
5. 计算 `标准电阻 − 实测电阻`，将结果写入该通道的 `calibrateValueArray`。
6. 在表格中显示实测电阻、标准电阻、本次补偿值、校准时间和状态，并把成功结果复制到“当前补偿值”。
7. 成功后自动保存全部通道的当前补偿值，同时保存顶部标准阻值。失败则记录错误并提示，不走成功保存路径。
8. 无论成功或失败，校准执行器的 `Finally` 路径都会复位中位机和 3562/34461 缓存。

## 六、批量校准流程

按事件处理代码的设计，选择多个通道后会先显示批量计划摘要，确认后才开始。当前源码的列名不一致可能使流程在读取勾选项时提前失败，详见第九节：

1. 按通道号排序选中项，禁用其他操作按钮，启用停止按钮，并设置进度条。
2. `ChannelCalibrationRunner` 将设备物理通道 1–128 放入 G1，129–256 放入 G2。G2 下发给中位机时使用本地编号：物理通道 129 对应 G2 本地通道 1，物理通道 256 对应本地通道 128。
3. 一次运行中位机计划，再读取与计划通道数相同的 3562 内阻记录。程序按计划执行顺序把缓存记录对应回通道。
4. 为每个返回通道计算补偿值并更新全局数组；页面逐行显示结果和进度。
5. 正常完成后保存全部 256 项当前补偿值及标准阻值，并记录批量成功/失败日志。
6. 运行异常会进入错误记录和提示；批量停止分支不会调用最终保存。

当前停止按钮只在批量流程中启用。单通道流程没有启用停止按钮的代码路径。批量缓存读取完成后，runner 会先把结果写入全局数组，再由页面逐行显示；如果此时在页面更新过程中停止，页面会跳过最终保存，因此内存中的新值可能与 CSV/数据库中的旧值暂时不一致。重新读取校准值可从持久化来源恢复页面数据。

## 七、补偿值如何作用于正式测试

校准值不是替换正式测试的原始读数，而是作为每个设备通道的偏移量参与结果回填：

```text
正式测试最终内阻（mΩ）= 3562 实测内阻（mΩ）+ 通道补偿值（mΩ）
```

`TwoPassResultMapper` 在正式测试回填内阻时执行加法；例如实测值 4.100 mΩ、补偿值 −0.070 mΩ，回填结果为 4.030 mΩ。正式测试仍按两遍流程采集；当只启用一组通道时，`FormalTestRunner` 按缓存规则取 3562 的实际内阻遍次。随后 OCV_DATA 的测试结果保存逻辑会用“最终内阻 − 补偿值”还原原始内阻，并分别保存原始值、补偿值和最终值。

因此，校准页面的“当前补偿值”影响后续正式测试；页面里的“本次补偿值”是这次标准件测量刚算出的结果。

## 八、保存、清零和数据校验

### 保存

点击“保存校准值”时，程序读取 256 行“当前补偿值”，逐项解析后写入全局数组；然后保存顶部标准阻值，最后保存补偿数组：

- 本地 CSV 保存 256 个 mΩ 数值；覆盖前会生成带时间戳的 `.bak` 备份。
- 保存前要求数组正好有 256 项；每个补偿值必须是有限数值，绝对值不得超过 1000 mΩ。
- CSV 写入后，程序读取数据库当前有效值，只将变化超过 0.000001 mΩ 的通道写入 OCV_DATA。
- 数据库写入时传入补偿值、操作员和备注；标准值、实测值参数在这段调用中传 `Nothing`。测量过程详情另外写入业务日志。
- 如果数据库写入失败，CSV 已在此前写完，因此可能出现本地文件已更新而数据库未更新的部分成功状态；页面会提示保存失败。

### 清零

“全部清零”先要求确认，再把界面 256 个当前补偿值设为 0、清空本次测量信息并把状态设为“已清零”。该按钮本身不立即持久化，需再点击“保存校准值”才能写入 CSV 和数据库。

## 九、源码中需要注意的界面绑定问题

当前工作区源码存在一个会影响实际操作的列名不一致，建议在依赖校准页执行生产校准前优先处理：

1. `FrmChannelCalibration.vb` 的动态表格初始化（其中会把列命名为 `Selected`、`ChannelNo`、`CurrentValue` 等）位于 `#If False Then` 条件块中，不会编译执行。当前构造函数只调用设计器的 `InitializeComponent()`。
2. 设计器实际创建的列名仍为 `DataGridViewCheckBoxColumn1`、`DataGridViewTextBoxColumn1` 至 `DataGridViewTextBoxColumn7`；本次中文化只设置了 `HeaderText`，没有改变这些 `.Name`。
3. 运行逻辑却用 `grid.Rows(...).Cells("Selected")`、`Cells("CurrentValue")`、`Cells("Status")`、`Cells("Measured")` 等名称访问列。

所以表格可以按位置显示 256 行，但在当前源码配置下，范围选择、选中通道、保存、清零和校准等路径可能在访问列时抛出“找不到列”的异常。`HeaderText` 是显示标题，不能替代 DataGridView 的 `Name`。此外，设计器没有设置其他文本列的 `ReadOnly`；动态初始化中原本对通道号、测量值等列的只读设置也处于禁用代码块内，当前控件默认允许编辑文本列。

这不改变上文描述的业务计算和数据流，但会阻断其部分页面操作。需要单独修复列 `Name`/运行时代码绑定，并明确哪些列允许编辑；本报告不包含该修复。
