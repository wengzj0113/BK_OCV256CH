# 主测试页手动模式代码审查（2026-10-21）

审查对象是当前工作区源码，包含未提交修改。范围为 `frmTest` 主页面的“手动”、启动测试、获取条码、停止、复位和 NG 点测；不包含独立 `FrmManualTest`。本轮没有修改应用程序源码，没有连接 PLC 或仪表。

结论：常规手动初测已经进入共同 PLC 协调器，但换盘优化尚未完整落实。旧托盘分选、模式/设置切换、停止恢复之间存在确定的状态管理缺陷；主页面 NG 点测另走直接测量路径，还有完成握手和托盘归属问题。

**确认的问题（按影响排序）**

1. **[P1] 旧托盘待分选时，切换模式或应用需重连 PLC 的设置会丢失旧 NG 集合。**

   `IsCycleOccupiedLocked` 在 `PlcAutomaticTestCoordinator.vb:272` 不再计入 `pendingNgSelection`。因此旧 R161 成功、当前周期清空后，即使旧分选尚未完成，`IsCycleOccupied` 仍为 False。`frmTest.vb:3955` 的模式保护和 `2668` 的设置保护随之放行；`3981` 或 `2745` 销毁旧协调器，新建实例没有旧 NG 快照。后续 R152 会走“未启动测试，跳过分选，直接 R162”的路径。临时假 PLC 复现确认：重建后没有新增 NG 档位写入，却发送了 R162。

   修正方向：恢复“完整未结周期”保护，单独提供“可接受下一手动托盘”的资格；只有托盘输入、获取码、选通道及启动使用这个资格，模式切换和客户端重建仍受旧分选保护。此前用全局删除占用项来解锁，只覆盖了部分场景。

2. **[P1] 停止/复位清掉已捕获的 R152，请求消费标记却仍保留，可能使旧 R162和新 R161一直无法完成。**

   `RequestStopCurrentCycle` 在 `PlcAutomaticTestCoordinator.vb:641` 无条件清空 `sortingRequestPending`，保留旧 `pendingNgSelection`，同时没有重置 `r152RequestConsumed`。触发：旧 R152 已经被捕获，NG档位或 R162 写失败后点击停止/复位；PLC仍保持 R152=1。下一轮读取会因为已消费标记不再捕获这个高电平，旧分选失去重试请求。后续新托盘完成时，又被 `1134` 的旧分选检查挡住 R161。

   临时假 PLC 已复现：R162 首次失败→停止→连续轮询 R152=1，R162 不再重试；下一托盘测完、保存后，R161仍不发送。修正方向是停止当前托盘时保留属于旧完成托盘的已捕获分选请求及其重试状态。

3. **[P1] 主页面 NG 点测另发 R160并等待 R151，但完成后不走 R161，旧分选集合也不更新。**

   `frmTest.vb:3739` 自行发送 R160，等待压合后在 `3767` 直接调用 `StarTest(0)`。此调用使用旧的直接保存及复测提示路径，返回后仅恢复界面，没有协调器的完成握手。窗体中的直接 `WriteR161` 在 `3653`，属于报警联动，正常 NG 点测不会执行它。由于没有向协调器提交新结果，旧 `pendingNgSelection` 仍是点测前的 NG 集合。

   影响：PLC收到开始通知并压合后，正常点测结束缺少对应完成通知；若旧托盘仍待分选，即使复测已经合格，后续仍可能按旧 NG 集合分选。应将 NG 点测纳入明确的协调器周期或定义完整的独立握手及分选结果更新规则。

4. **[P1] 换托盘后，NG 点测可以沿用上一托盘的 NG 通道，以新托盘码保存。**

   `frmTest.vb:3693` 从全局 `retestArray` 取得 NG 点，只验证当前托盘码格式，没有检查 NG 集合所属托盘。`3789` 的托盘文本变化只更新字符串；`1816` 的新托盘准备清空旧电芯码/测量值并装入新码，却不清除 `retestArray`。触发：托盘 A 初测有 NG→输入托盘 B并获取电芯码→点击 NG 点测。程序会使用 A 残留的 NG 通道去测 B，并以 B 的托盘码保存。B缺少这些通道电芯码时还可能保存失败。

   修正方向：NG 集合与托盘码、任务及电芯码快照绑定；更换托盘使旧点测资格失效。

5. **[P2] 旧 NG 档位或 R162 通信重试期间，下一手动托盘仍被锁住。**

   `PlcAutomaticTestCoordinator.vb:275` 把 `sortingRequestPending` 计入占用；档位/R162失败会保留该请求并进入 WaitingR152/WaitingR162Ack。`RequestManualCycle` 在 `221` 只接受 Idle；界面 `frmTest.vb:4015` 同时以占用状态锁住输入、获取码及启动。临时假 PLC 已确认该状态下新请求返回 False。

   已确认的换盘方案要求旧分选重试不占用新托盘上下文。当前只在“旧 R152 尚未到达”的窗口解锁，重试窗口尚未实现。

6. **[P2] 稀疏手选通道的 NG 点测集合会遗漏高位通道，也可能保留已复测合格的通道。**

   `FreshBat` 在 `frmTest.vb:1413` 已使用实际选择通道判断，`1416` 又按起点和数量推导连续范围。例如手选 CH1、CH256，起点1、数量2会把 CH256排除，`1466` 不会给该点写 NG 标记。后续 NG 点测漏掉这个实际测出 NG 的通道。另该函数只给 NG置1，没有为转OK的通道清0；`3058` 在自动复测前清空后预置本轮通道，复测转OK的点仍可残留为待NG点测。

   配置的协调器自动 NG 复测通过 `BuildAutomaticPassResult` 取得结果，不直接依赖这个错误范围；受影响的是主页面 NG 点测及旧 NG 标记。

**需要现场协议确认的边界**

- 每轮手动 R160发送成功后，`PlcAutomaticTestCoordinator.vb:878` 将 `r151RequestConsumed=False`。如果上一托盘 R151始终保持1，下一托盘可能在首次读取这个持续高电平时立即测量；程序没有要求先看到0再接受新一轮1。需要明确 PLC 是否保证跨托盘复位，不能直接把该情形判为已确认代码缺陷。
- 之前现场日志能证明上位机读取到 R151=0，因此没有进入测量。R160“已发送”只说明串口写调用成功；日志不能单独证明 PLC已收到R160，也不能单独证明 PLC内部R151没有置位。需要对照PLC监控值或原始收发帧确认。
