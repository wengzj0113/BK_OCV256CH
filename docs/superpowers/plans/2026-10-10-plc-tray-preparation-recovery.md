# 自动托盘数据准备失败恢复优化实施方案

> **For agentic workers:** 按本文分阶段实施。实现前先核对本计划对应的未提交工作区改动；状态转换与恢复路径先由自动化回归用例锁定，再改生产逻辑。此计划不授权覆盖或清理其他工作区改动。

**目标：** 托盘码已扫码但电芯码查询/校验失败时，让操作员可以在当前 R150 请求上切换调试模式并继续，或在数据库/托盘数据修复后重试；无需重启上位机或复位全部 PLC 动作。

**架构：** `PlcAutomaticTestCoordinator` 保持为 PLC 自动流程的唯一状态机，新增“托盘准备待恢复”状态及保留的托盘请求上下文。上位机先在局部变量中完成电芯码查询与测试计划校验，成功后一次性提交托盘快照，再写 R160；可恢复的准备错误不进入通用 `Fault`，也不确认 R160。操作员切换调试模式或点击重试时，协调器只重做当前托盘准备；观测到 R150 归零后才释放旧请求并接受下一次 R150 上升沿。

**技术栈：** VB.NET 4.8 WinForms、现有 `PlcAutomaticTestCoordinator`、`IPlcAutomationClient`、SQL Server 存储过程、PowerShell 源码与运行时检查、现有 x86 Debug 构建。

---

## 1. 现状和故障原因

当前自动流程在 `PlcAutomaticTestCoordinator.AcceptTrayCode` 中依次调用 `SetTrayCode`、`PrepareAutomaticTray`，然后才把托盘码写入 `cycle.TrayCode` 并准备写 R160。正式模式的 `PrepareTrayForTest` 会查询 `dbo.usp_GetTrayCellsByTrayCode`，再调用 `TrayTestPreparation.Prepare` 校验托盘数据。

准备过程发生异常时，异常返回 `ProcessPendingRequests` 并进入通用 `EnterFault`。此时：

- 本次 `R150=1` 已被 `r150RequestConsumed` 消费，`trayRequestPending` 也已取走。
- 托盘码没有进入 `cycle.TrayCode`，没有专门保存为可重试的准备上下文。
- `Fault` 没有“按当前托盘重新准备”的状态转换；调试复选框变化只清空缓存、更新模式，不会重试协调器里的请求。
- 新一轮 R150 请求只在成功读到 `R150=0` 后重新使能。持续为 1 的同一次请求不会被重复消费。
- `PrepareTrayForTest` 在查询前就清除 `activeTrayPlan` 和全局电芯码；如果后续失败，界面和本轮准备状态已改变，但没有可提交的完整托盘快照。

因此故障是**托盘预检异常被提升为整个自动流程故障，且原请求没有可恢复上下文**。调试模式能绕过数据库查询，但只能影响一次新的准备调用；当前实现没有在模式变化时重做这次调用。

程序代码中的输入名是 `R150`。若现场 HMI 标为 `A150`，实施前须确认二者是同一个 PLC 信号或地址映射；下文以代码契约 `R150` 表述。

## 2. 目标行为与边界

### 目标行为

1. 扫码得到有效托盘码后，保存为“待准备托盘”，但在计划完整前不将其标成已接收周期，不写 R160，不启动 R151 测试。
2. 生产数据查询、数据完整性校验或计划构建失败时，进入可恢复的 `WaitingTrayPreparationRecovery`，保留托盘码、失败类别、原因和当前请求代次。
3. 当 R150 仍为 1 时，操作员开启调试模式后，自动对保留的同一托盘码执行一次调试准备；准备成功后继续现有 R160 → R151 流程。
4. 数据库或映射修复后，操作员可点击“重试准备”，在当前模式下重查同一托盘码。每次点击最多排入一次尝试，不循环访问数据库。
5. 若要换托盘，收到 R150=0 后丢弃尚未确认的旧托盘准备上下文；下一次 R150 从 0 变 1 时重新扫码并准备新托盘。
6. 仅在托盘计划已完整建立后写 R160。R160 通讯异常沿用现有确认重试逻辑，不重复查询、生成计划或启动测试。
7. 调试准备生成的结果继续标记为 Debug，并沿用现有不上传生产 MES 的保护。

### 范围

只处理**测试尚未开始、R160 尚未成功确认之前**的托盘数据准备恢复。扫码器本身的超时/无效码手工输入、测试过程异常、正式结果保存、R161/R162 失败策略、PLC 报文和测量算法不在本次重设计范围内。实现时必须保留这些既有行为，尤其不得把测试/保存异常降级成托盘准备错误。

## 3. 方案比较与选择

| 方案 | 行为 | 风险/代价 | 结论 |
|---|---|---|---|
| A. 继续使用通用 Fault，要求完整复位 | 失败后重启协调器或重置 PLC/上位机 | 复现现状，无法满足当前请求恢复 | 不采用 |
| B. R150 高电平期间自动定时重试 | 每轮轮询重复查询数据库或重扫 | 数据库无映射时反复打库；可能重复扫码或错误接受另一只托盘；故障原因被噪声淹没 | 不采用 |
| C. 保留请求并做显式、单次重试 | 数据准备错误进入专用恢复状态；调试模式变化自动重做一次；按钮允许按当前模式手动重试；R150 低电平释放旧请求 | 增加一个协调器状态、一个重试入口和清晰的错误分类 | **采用**：重试次数可控、保留现场、满足高电平下当前请求继续，同时不破坏 PLC 的单次请求语义 |

## 4. 推荐技术设计

### 4.1 状态与数据模型

在 `PlcAutomaticTestState` 增加 `WaitingTrayPreparationRecovery`。该状态表示：扫码与托盘码校验已完成，数据库/计划准备失败；当前托盘码仍属于尚未确认的 R150 请求；`R160` 尚未成功写入；未启动测试。

协调器增加一个待准备上下文，至少包含：

| 字段 | 用途 |
|---|---|
| `TrayCode` | 本次已校验的原始托盘码；重试不得从可编辑 UI 文本重新取值 |
| `RequestGeneration` | 丢弃停止、取消或新请求后迟到的回调 |
| `FailureKind` | 区分无电芯映射、数据无效、数据库访问失败 |
| `LastFailureMessage` | UI 状态与操作日志显示的具体原因 |
| `RetryQueued` / `PreparationInProgress` | 去重按钮和模式变化引发的重试，避免并发准备 |

待准备上下文与 `AutomaticTestCycle` 分开：准备失败时 `cycle.TrayCode` 仍为空；准备成功、候选计划提交后，再将托盘码写入周期并置 `trayConfirmationPending`。不要通过填入 `cycle.TrayCode` 来阻止重复处理，因为后续完成周期会依赖该字段判断。

状态规则：

| 当前状态 | 输入/动作 | 下一步 |
|---|---|---|
| `Idle` | R150 首次/新上升沿为 1 | 记录请求、扫码 |
| `ReadingTrayCode` | 扫码成功且托盘码有效 | 保存待准备上下文，准备候选计划 |
| 准备阶段 | 候选计划完整 | 原子提交计划与电芯码；设置周期托盘码；写 R160 |
| 准备阶段 | 预期的数据查询/校验失败 | 保留待准备上下文，转 `WaitingTrayPreparationRecovery`；不写 R160 |
| `WaitingTrayPreparationRecovery` | 调试模式从关变开 | 排入当前托盘的一次调试准备 |
| `WaitingTrayPreparationRecovery` | 操作员点击“重试准备” | 排入当前模式的一次准备尝试 |
| `WaitingTrayPreparationRecovery` | 读取到 R150=0 | 丢弃未确认上下文并返回可接收新请求的空闲边界 |
| `WaitingTrayPreparationRecovery` | 同一 R150 高电平继续保持 | 保持等待；除显式重试外不重新扫码、不重新查询 |
| 任一准备状态 | 操作员停止/请求代次失效 | 丢弃回调及待准备上下文；保留现有停止语义 |

若现场 PLC 故障时不把 R150 拉低，则单靠电平无法判断“旧请求持续为 1”还是“新托盘重新进站”。软件不得把持续高电平伪装成第二个上升沿。恢复当前请求仍可通过切换调试模式或点击重试完成；新托盘须等待 PLC 复位并重新置位，或在现场协议确认后提供明确的“重新扫码当前请求”人工动作。是否需要后者由现场握手确认决定，不得自动猜测。

### 4.2 准备结果分类

将可恢复数据准备失败用明确类型传递到协调器，例如 `TrayPreparationException` + `TrayPreparationFailureKind`：

| 类别 | 来源 | 恢复动作 | 是否进入通用 Fault |
|---|---|---|---|
| `NoBatteryMapping` | 存储过程成功返回 0 行，或无可用电芯码 | 开启调试模式继续，或更正映射/换托盘后重试 | 否 |
| `InvalidTrayData` | 空电芯码、非法/重复通道、重复电芯码等 `TrayTestPreparation` 校验失败 | 更正托盘数据、开启调试模式或换托盘后重试 | 否 |
| `DataAccessFailure` | SQL 连接、超时、权限或存储过程访问失败 | 点击重试准备；也可在授权调试流程中切到调试模式 | 否 |
| 未分类程序/设备异常 | 空引用、状态不变量破坏、PLC 通讯等非预期故障 | 按原故障策略处理 | 是 |

分类必须基于具体来源，不得用 `Catch Exception` 把所有异常变成可恢复状态。数据库异常仅在数据库调用边界归类；测试执行与结果上传的异常继续沿原处理路径。

### 4.3 候选计划原子提交

把准备拆成两个明确阶段：

1. **构建候选：** 查询托盘单元；由 `TrayTestPreparation.Prepare` 完成通道、电芯码及自动/手动规则校验；调试模式由 `DebugBarcodePolicy` 构建临时电芯码。此阶段只操作局部 `DataTable`、`TrayTestPlan` 和候选电芯码，不写 `activeTrayPlan` 或 `RecieveData`。
2. **提交候选：** 仅候选计划完整后，在 UI 线程一次性设置 `activeTrayPlan`、256 通道的电芯码和调试标记，再刷新通道概览。任何候选构建失败都不产生部分映射，不留下前一托盘的电芯码。

新请求第一次开始准备时，先清理前一托盘显示缓存；同一待准备请求的重试只重建候选，不反复清空/写入全局数组。候选提交和协调器周期状态提交都必须受当前 `RequestGeneration` 校验保护。

### 4.4 重试触发和幂等性

- `DebugTestModeCheckedChanged` 在 `WaitingTrayPreparationRecovery` 中允许操作员改变调试模式。只有模式从关闭切到开启时自动排入一次调试准备；切回关闭只改变选择，不自动查询数据库。
- 新增一个仅在该恢复状态显示/启用的“重试准备”按钮。点击后，使用已保存托盘码和当前模式排入一次准备；它主要覆盖数据库短暂不可用、托盘数据修复等场景。
- UI 事件只向协调器提交重试请求；由协调器设置 `RetryQueued` 并在轮询中消费，防止 UI 线程与 PLC 轮询线程并发改周期状态。
- 单次准备失败后更新最后错误并保持恢复状态，不自动循环重试。重复按钮点击、同一模式的重复 `CheckedChanged`、重复的 PLC 高电平都不能造成重复扫描/查询并发。
- 准备成功后清除待准备上下文，建立正式周期状态并继续 `ConfirmTrayCodeWithPlc`。R160 写入失败仍按现有 `trayConfirmationPending` 重试；重试 R160 时不再查询数据库、不重新生成调试码、不重做其他设备动作。

### 4.5 PLC 信号和命令不变量

1. 上位机只读 R150；恢复逻辑不得写 R150，也不得伪造低电平。
2. 每个 R150 高电平请求最多扫码一次；准备失败后保留此请求，不因为轮询继续读取到高电平就重新消费。
3. 只有完整计划提交后才写 R160=1；数据库无数据、数据非法、准备异常时禁止 R160、R151 启动和任何 OCV_DATA 任务创建。
4. 读到 R150=0 才重新使能下一次上升沿，并清除尚未确认的准备请求。下一次 0→1 必须重新扫码，不能复用旧托盘码。
5. 本次流程不改 R151/R152/R161/R162 协议，不写测试相关输出寄存器来“复位”故障。

### 4.6 UI 与诊断信息

- `WaitingTrayPreparationRecovery` 的主状态文案显示托盘码、错误摘要、当前模式，以及“未写 R160、测试尚未启动”。例如：`托盘 TRAY-001 未查到有效电芯码；开启调试模式可用临时码继续，或修复数据后点击重试。`
- 事件日志区分 `托盘准备失败`、`已排入重试（模式=调试/正式）`、`候选计划构建成功`、`托盘准备提交成功`、`等待 R150 归零`、`因 R150=0 已释放旧请求`。查询异常日志保留内部异常类型与简明原因，但避免打印连接字符串或凭据。
- 故障状态切换时刷新 `chk_Test` 和重试按钮可用性。调试模式只在空闲或托盘准备恢复状态允许切换；已成功准备并进入 R160/R151 流程后继续锁定。

## 7. 验收矩阵

| 场景 | 预期状态/动作 | 必须禁止 |
|---|---|---|
| 正式模式下扫码成功，但托盘查询为 0 行 | 恢复等待；保留扫码托盘码；日志说明没有有效电芯映射 | R160、R151 测试启动、结果任务创建、自动反复查库 |
| `R150=1` 保持期间开启调试模式 | 对同一托盘码生成 Debug 候选计划；提交成功后只写一次 R160；等待现有 R151 | 再次扫码、正式 DB 查询、生产 MES 上传 |
| DB 短暂异常，操作员点击重试 | 当前模式下对保留托盘码重试一次；失败则留在恢复状态，成功后继续 R160 | 并发/无限重试、重复提交计划 |
| 托盘数据修正后重新点击 | 使用数据库最新结果构建候选；完整验证后原子提交 | 复用旧 `RecieveData` 或半成品映射 |
| 恢复状态收到 `R150=0` | 清除旧准备上下文；等待新上升沿 | 把 R150 低电平当成新托盘、复用旧托盘码 |
| 旧 R150 高电平未复位 | 保持单个请求等待；只有操作员显式重试才尝试继续 | 将每次高电平采样解释成新请求 |
| 准备成功后 R160 写入失败 | 保持待确认状态并重试 R160 | 再次查询数据库、再次生成计划、开始测试 |
| 初测、复测、保存或未知程序错误 | 保持现有 Fault/停止处理 | 当作可恢复托盘预检错误自动继续 |

## 8. 现场联调与风险控制

1. **先核对信号标签。**从 PLC 监控页或现场地址表确认用户所说 A150 是否就是程序读取的 R150。若不是，先修正地址映射结论，不能以名称相似推断。
2. **记录一个完整失败周期的电平。**在托盘准备失败期间观察托盘移出、重新放入时 R150 的 1/0 时序，并确认 R160 是否是 PLC 释放 R150 的必要握手。
3. **确认 R150 清零含义。**本计划只在确认读到 0 时自动释放待准备的旧托盘请求。若 R150 是必须等 R160 才能复位的保持型请求，则“无映射失败后换新托盘”无法仅凭该位自动识别；需与 PLC 负责人约定故障取消/新托盘请求的明确方式，再确定是否加入人工重新扫码入口。
4. **优先先软件离线验收，再联机空托盘/调试托盘验证。**联机第一阶段确认失败时 R160 不输出；第二阶段在批准的调试模式下观察一次准备恢复和 R160；第三阶段验证低电平释放及下一次上升沿。逐阶段留存上位机事件日志和 PLC 监控截图。
5. **回滚边界。**若现场握手解释与上述约定不符，停止继续自动运行并回滚本次上位机版本；不通过向 PLC 输入位写值或清空所有 PLC 输出作为软件补救。

## 9. 实施完成定义

满足验收矩阵、既有 PLC 握手回归和 Debug/MES 隔离检查，Debug/x86 构建成功；现场确认 R150/A150 映射和复位规则后，分别记录软件自动恢复与换托盘重入的实机结果。任何一个 PLC 信号合同未确认时，只能报告软件离线验证完成，不能把现场换托盘恢复标为完成。
