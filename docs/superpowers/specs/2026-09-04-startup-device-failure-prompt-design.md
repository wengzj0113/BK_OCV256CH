# 启动设备检查失败提示设计

## 目标

启动阶段完成外部设备检查后，如果有设备连接失败，向用户明确提示失败设备和可诊断原因；成功设备不弹窗。提示只出现一次，不阻塞后台检查，也不改变现有设备通信流程。

## 当前问题

`StartupDeviceService` 在后台线程顺序检查控制模块、34461、3561、PLC 和 MES。检查结果会更新底部状态栏，但失败结果没有面向用户的汇总提示。控制模块检查失败时，`CheckCom_SCM` 内部还会吞掉异常并返回 `-1`，导致上层只能看到失败状态，无法显示具体原因。

## 设计

1. 启动检查服务继续在后台线程执行，避免阻塞首屏。
2. 每个设备检查保留状态码，并为失败项记录可读的失败原因。
3. 所有检查完成后，在 UI 线程通过 `BeginInvoke` 更新状态栏并显示一次汇总 `MessageBox`。
4. 汇总提示仅在存在失败项时显示，内容包含设备名称、通信方式/地址和失败原因。
5. 成功项不列出；没有失败项时不弹窗。
6. 关闭弹窗后，状态栏仍显示每个设备的最终连接状态。
7. 失败提示不能从后台线程直接调用 `MessageBox`，不能为每个设备分别弹窗，也不能伪造连接成功。

## 控制模块失败信息

控制模块使用串口时，提示至少区分：

- 串口打开失败；
- 串口已打开但协议握手超时、没有返回帧；
- 收到返回帧但协议校验或长度不正确。

当前已确认 `COM14` 的典型失败是协议握手超时：端口配置为 `115200/8N1`，发送 `AA 03 00 40 00 07 1C 07` 后 3 秒无返回。

## 测试与验收

- 启动检查包含失败设备时，弹出一个汇总提示，且只弹一次。
- 启动检查全部成功时，不弹失败提示。
- 控制模块握手超时时，提示中包含 `COM14`、超时/无返回帧等关键信息。
- 后台检查完成后状态栏结果不受弹窗影响。
- 既有启动、通信、设计器和构建回归检查继续通过。
