OCV_DATA 最终数据库设计文档

项目：XL_OCV_256CH 日期：2026-08-02 目标数据库：OCV_DATA 适用范围：256 通道 OCV/ACIR 测试、扫码托盘、电芯结果、复测、校准、查询、MES 离线队列

1. 设计结论

新数据库不能只替代旧的 CW_tblData_Info。当前上位机代码中的数据库操作同时覆盖托盘、条码、测试结果、查询分档、MES 上传缓存和设备日志，因此 OCV_DATA 需要设计成上位机数据访问的深模块：上位机通过少量存储过程完成业务操作，数据库内部负责表结构、历史版本、最新结果汇总、分档规则和离线队列。

最终建议：采用规范化表结构保存真实历史数据，同时提供 vw_CellTestSummary 视图兼容旧查询界面的横向 OCV1/OCV2/OCV3/OCV4 显示方式。
关键修正：上一版方案缺少分档规则、旧查询汇总视图、上传离线队列和托盘绑定历史。本版已补齐这些能力。

3. 核心业务规则

托盘与通道

  • 目标系统支持 1-256 物理通道。
  • 托盘允许空位，查到多少电芯条码就绑定多少通道。
  • 通道映射暂按当前界面逻辑：ChannelNo = (ColNo - 1) * 16 + RowNo。
  • 同一托盘允许重新绑定，历史通过 BindVersion 保存。

测试结果

  • 每次开始测试创建一条 TestTask。
  • 每个被测通道保存一条 TestResult。
  • 同一电芯同一 OCV 阶段允许多次测试，查询默认取最新一次。
  • NG 复测不覆盖历史，另建任务并记录复测关系。

校准

  • CalibrateValue 单位按 mΩ 保存。
  • 正式结果保存原始内阻、校准值、最终内阻。
  • 校准表保留历史，当前值通过 IsActive = 1 标识。

上传与日志

  • MES 上传失败进入 UploadOutbox，后续重传。
  • MesUploadLog 保存上传摘要和响应。
  • 中位机、3562、34461 的关键命令摘要进入 DeviceCommLog，原始详细日志仍可保留文件。

9. 实施计划

  1. 创建 OCV_DATA 数据库和基础表：Tray、TrayCell、TestTask、TestResult。
  2. 创建托盘和测试结果相关存储过程，先支撑扫码和正式测试落库。
  3. 创建 vw_CellTestSummary，验证查询界面可通过视图拿到旧格式字段。
  4. 创建分档规则表和存储过程，迁移 CW_tblCondition/CW_tblSelFld 能力。
  5. 创建 UploadOutbox，迁移 MES 离线缓存能力。
  6. 创建校准、通讯日志、报警和能耗相关表。
  7. 新增上位机数据库访问 Adapter，例如 OcvDataRepository，统一封装存储过程调用。
  8. 逐步替换旧 clsDB 的直接 SQL 调用，优先替换扫码托盘和测试结果保存。
  9. 完成查询/导出切换后，再移除对旧 CWSQL 表的依赖。

10. 风险与待确认事项

必须确认：现场托盘位置是否最终采用列优先映射 ChannelNo = (ColNo - 1) * 16 + RowNo。如果数据库或 MES 使用行优先，只需要替换 usp_SaveTrayCells 内部映射或上位机导入映射。
  • 远端托盘条码接口尚未提供，因此 TrayCell 的数据来源需要先支持手工导入或后续接口写入。
  • 旧查询界面使用 VBScript 表达式计算分档，后续建议由数据库或上位机专门规则引擎替代。
  • 旧代码中 OCV 阶段命名 A/B/C/D 与界面 OCV0/OCV1/OCV2 需要在改造前统一定义。
  • MES 上传 JSON 量较大，UploadOutbox.PayloadJson 使用 nvarchar(max)，同时需要定期归档。
  • 设备日志量可能增长很快，DeviceCommLog 建议只保存关键摘要，详细原始帧继续保留文件。

11. 补充的生产级设计

再次检查后，原方案已经覆盖了当前代码里的主要读写动作，但要真正支撑产线长期运行，还需要把“重复提交、并发写入、数据归档、规则版本、接口追溯、权限和恢复能力”明确纳入设计。下面这些内容建议作为最终数据库方案的一部分，而不是后续临时补丁。

11.1 幂等与重复提交防护

场景 风险 设计补充
保存测试结果 软件重试、重复点击、异常恢复后可能重复写同一盘同一阶段数据。 TestTask 增加 IdempotencyKey；TestResult 保持 TestTaskId + ChannelNo + MeasurementType 唯一；usp_SaveTestResults 必须支持重复调用不重复插入。
托盘明细保存 扫码后多次触发 txtTray_TextChanged，或接口重试导致通道条码重复。 usp_SaveTrayCells 按 TrayId + ChannelNo 做 upsert；同一托盘同一通道只保留一条当前记录，历史变更进入审计表。
MES 上传队列 断网恢复后重复入队，导致同一测试结果多次上传。 UploadOutbox 增加 IdempotencyKey，建议由 TrayCode + OcvStage + TestRound + UploadType 生成唯一键。

11.2 并发、锁定与多实例防护

  • 关键主表建议增加 RowVersion rowversion：Tray、TrayCell、TestTask、GradeScheme、ChannelCalibration。
  • UploadOutbox 需要增加 LockedBy、LockedAt、NextRetryAt，防止多个上位机实例或多个定时器同时上传同一条队列。
  • 同一托盘同一 OCV 阶段是否允许重新测试，应由 usp_CreateTestTask 判断；允许重测时必须生成新的 TestRound，不允许静默覆盖整盘历史。
  • 正式测试开始时，建议把 TestTask.Status 从 Created 改为 Running，结束后改为 Completed 或 Failed；异常退出的任务可由恢复逻辑识别。

11.3 OCV 阶段、规格限值与规则版本

当前代码和历史数据里存在 OCV0/OCV1/OCV2、currentOCVNum、A/B/C/D 后缀等多套命名。新库不建议继续硬编码这些含义，应增加阶段和规格版本表。

OcvStage
- OcvStageId
- StageCode          -- OCV0 / OCV1 / OCV2
- LegacyStageNo      -- 兼容 currentOCVNum
- LegacyColumnSuffix -- 兼容旧查询 A/B/C/D
- DisplayName
- MesStageCode
- SortOrder
- IsActive
TestSpec
- TestSpecId
- SpecName
- OcvStageId
- EffectiveFrom
- EffectiveTo
- IsActive
- CreatedAt

TestSpecLimit
- TestSpecLimitId
- TestSpecId
- MeasurementType    -- Voltage / Resistance
- LowerLimit
- UpperLimit
- UnitName           -- V / mOhm
- NgCode

TestResult 建议记录本次判定使用的 TestSpecId，或者直接冗余保存当时的电压/内阻上下限。这样后续修改参数后，历史结果不会被新规则“重新解释”。

11.4 单位、精度与校准值口径

  • 电压建议以 VoltageVolt decimal(18,9) 作为主存储单位，毫伏显示通过视图或计算字段得到。
  • 内阻建议以 ResistanceMilliohm decimal(18,6) 作为主存储单位。
  • calibrateValueArray(ch) 已明确按 mΩ 保存，因此 ChannelCalibration.CalibrationValueMilliohm 必须用 mΩ 命名，避免后续误按 Ω 叠加。
  • 如果保存原始值和校准后值，字段应明确区分：RawResistanceMilliohm、CalibrationValueMilliohm、FinalResistanceMilliohm。

11.6 审计、人工修改与文件追溯

条码、分档规则、校准值、系统参数都可能被人工修改。只保存最终值不够，需要能回答“谁在什么时候改了什么”。

AuditLog
- AuditId
- EntityName
- EntityKey
- ActionName       -- Insert / Update / Delete / Approve / RetryUpload
- BeforeJson
- AfterJson
- OperatorName
- WorkstationName
- CreatedAt
FileArtifact
- FileArtifactId
- ArtifactType     -- LocalCsv / MiddleMachineLog / InstrumentLog / ImportFile
- TestTaskId
- TrayCode
- FilePath
- FileHash
- CreatedAt

本地 CSV、串口日志、导入文件不是数据库的替代品，但它们是追溯证据。建议至少保存文件路径、文件类型、生成时间和哈希值。

11.7 外部接口与未来托盘明细服务

远端托盘接口当前尚未提供，因此新库要同时支持本地导入和未来接口接入。建议增加接口调用记录：

ExternalSyncLog
- ExternalSyncLogId
- SourceName        -- TrayApi / MesApi / ManualImport
- BusinessKey       -- TrayCode / TaskCode
- RequestJson
- ResponseJson
- IsSuccess
- ErrorMessage
- CreatedAt
  • TrayCell.SourceType 保留 RemoteApi、LocalDb、ManualImport、ManualEdit。
  • 未来接口返回空位时，数据库应允许 BatteryCode 为空，但 ChannelNo 仍然保留，以便区分“空位”和“未返回”。
  • 托盘条码只作为入口，不应把扫码程序返回的整串内容直接当作电芯明细；电芯明细必须来自托盘明细表或接口响应。

11.8 权限、备份和启动健康检查

  • 建议建立 SQL 角色：ocv_app_writer 只能执行上位机需要的存储过程；ocv_query_reader 只能读视图和报表过程；ocv_admin 管理结构和基础配置。
  • 上位机原则上调用存储过程，不直接拼 SQL 写核心表；这样可以把唯一性、幂等、审计和事务封装在数据库层。
  • 增加 SchemaVersion 表，记录数据库版本、升级脚本编号和升级时间；上位机启动时检查版本，不匹配则提示禁止测试。
  • 增加 usp_CheckDatabaseHealth：检查数据库连接、版本、关键表是否存在、待上传失败数量、未完成测试任务数量。
  • 备份建议采用完整备份 + 差异备份 + 日志备份；上线前至少做一次恢复演练，确认能恢复到指定时间点。

11.9 数据库落地验证清单

  1. 空托盘、部分通道托盘、满盘 256 通道托盘均可保存并查询。
  2. 同一托盘同一通道重复保存时不会产生重复当前记录。
  3. 连续通道、零星通道、跨 G1/G2 通道的测试结果均可按通道正确落库。
  4. NG 复测只覆盖或更新指定 NG 点，数据库、CSV、MES 出口口径一致。
  5. 修改分档规则或上下限后，历史结果仍按当时规则可追溯。
  6. MES 上传失败后进入重试队列，重复执行上传任务不会重复入队。
  7. 校准值修改会写入审计，正式测试保存原始内阻、校准值和最终内阻。
  8. 数据库版本不匹配、连接失败、关键存储过程缺失时，上位机禁止开始测试。
